# 项目执行模型（2026-08-02）

## 目的

避免项目因长上下文、多人次会话或技术细节过多而偏离目标。项目采用“主会话裁决 + 独立子会话实施 + 报告回传审核”的模式。

## 角色

### 主会话

主会话向用户负责，只做：

1. 理解并确认项目目标、约束与验收标准；
2. 判断当前优先级、技术路线和风险；
3. 把工作拆成边界小、可验收的工作单；
4. 审核子会话完成报告，判断是否可信、是否越界、是否需要纠正；
5. 用用户能理解的语言说明真实状态、项目影响、风险和下一步选择。

主会话不得自行实施业务任务：不运行实施命令、不修改业务代码、不读写数据库、不调用 API、不处理<local-scratch>、不执行入库/验证/生成、不提交或推送。用户明确要求主会话更新项目规则或短总览时，仅可维护这些文档状态。

### 实施子会话

每个子会话：

1. 只执行一个编号唯一的工作单；
2. 建议预算 100--250k token，完成、阻断或超预算后退役；
3. 只读取工作单允许的最小上下文；
4. 只修改工作单列出的文件；
5. 自己执行核验、测试、Git 提交和推送；
6. 写完成报告，并把报告回传主会话。

不允许把已完成子项目继续拿来做另一项实施工作，避免历史上下文污染。

## 工作单必须写清楚

- 子项目编号、目标和非目标；
- 输入、前置条件、允许/禁止修改的范围；
- 执行步骤、验收标准、验证命令；
- 数据库/API/源文件/Git 的边界；
- Token 与成本上限（如适用）；
- 失败处理和停止条件；
- 回传给主会话的具体内容。

用户未明确批准前，主会话只能准备候选工作单，不能视为已启动。

## 完成报告必须分两层

### 人话说明

用非技术语言交代：要解决什么、实际做了什么、结果是什么、为什么重要、风险/未完成项、建议的下一步。不得省略失败和阻断。

### 技术事实

列明：修改文件、实际命令、测试/核验结果、数据样本/哈希/API 成本等真实数字、Git 提交哈希、推送结果、最终 `git status -sb`。

禁止：把未执行写成通过；把估算写成实测；把推测写成根因；把模型结论写成源文件事实；泄露 API 密钥或<local-scratch>。

## 进度恢复

恢复时先读 `AGENTS.md` 和 `task_plan.md`，再读用户批准的工作单、该范围 Git 状态/差异与最小相关报告。不能因候选工作单存在就自动开始执行。

## 当前适用的项目方向

可信源题目的正确性以源文件为准。当前优先验证的是“源文件 -> 数据库”的保真度，而非让 LLM 重新解题。API 只在生成阶段辅助选题、组织和讲解，且不得改写源题内容。详见 `docs/designs/validation_strategy_revision.md`。

MATH-VALIDATION-005 已因策略调整终止，不得恢复；其部分实验结果不得写入正式数据库，也不得作为题目放行或阻断依据。
